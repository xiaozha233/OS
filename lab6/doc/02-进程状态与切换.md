## 1. 进程状态回顾 [S06]

### 1.1 知识卡片：进程状态

| 字段 | 内容 |
|:---|:---|
| **名称** | 进程状态（Process State） |
| **要解决的问题** | 操作系统需要知道每个进程当前处于什么阶段，以便正确管理和调度 |
| **先修要求** | 理解什么是进程、进程控制块（PCB） |

#### 类比 / 直觉

想象一个餐厅的顾客状态：
- **等位中**（UNINIT）：刚到餐厅，还没安排座位
- **就餐中**（RUNNABLE）：已经坐下，可以点餐或正在吃饭
- **等菜中**（SLEEPING）：点完菜在等上菜，暂时无事可做
- **结账离开**（ZOMBIE）：吃完了，等待买单离开

#### 形式化表述

在 ucore 中，进程有以下四种状态，定义在 `kern/process/proc.h` 中：

```c
enum proc_state {
    PROC_UNINIT = 0,  // 未初始化状态
    PROC_SLEEPING,    // 睡眠/阻塞状态
    PROC_RUNNABLE,    // 就绪/运行状态
    PROC_ZOMBIE,      // 僵尸状态（已退出，等待回收）
};
```

#### 状态含义详解

| 状态 | 含义 | 触发条件 |
|:---|:---|:---|
| `PROC_UNINIT` | 进程刚分配 PCB，尚未初始化 | `alloc_proc()` 分配后 |
| `PROC_RUNNABLE` | 进程可运行，等待或正在使用 CPU | 初始化完成 / 被唤醒 |
| `PROC_SLEEPING` | 进程等待某事件（锁、I/O、sleep） | 主动等待资源 |
| `PROC_ZOMBIE` | 进程已退出，资源待父进程回收 | 调用 `exit()` 后 |

### 1.2 进程生命周期

```
    alloc_proc()                                   正在运行
        │                                        ┌──────────┐
        ▼                                        │          │
  ┌───────────┐   初始化完成    ┌───────────┐   │ proc_run │
  │PROC_UNINIT│ ────────────▶ │PROC_RUNNABLE│◀──┴──────────┴──▶┐
  └───────────┘               └─────┬───────┘                   │
                                    │                           │
                    ┌───────────────┼───────────────┐           │
                    │               │               │           │
                    ▼               ▼               ▼           │
              wait/sleep       时间片用完        do_exit        │
                    │               │               │           │
                    ▼               │               ▼           │
            ┌───────────┐           │       ┌───────────┐       │
            │PROC_SLEEPING│◀────────┘       │PROC_ZOMBIE│       │
            └─────┬─────┘                   └───────────┘       │
                  │                               ▲             │
                  │        wakeup_proc()          │             │
                  └───────────────────────────────┴─────────────┘
```
[Fig·S06-2]: 进程状态转换图，展示完整的生命周期流程

#### 生命周期详细步骤 [S07]

1. **创建阶段**：`alloc_proc()` 分配 PCB，状态为 `PROC_UNINIT`
2. **初始化完成**：完成初始化后，进入 `PROC_RUNNABLE` 状态
3. **获得调度**：调度器选中该进程，`proc_run()` 执行
4. **可能路径 A**：进程调用 `wait`/`sleep` 阻塞，进入 `PROC_SLEEPING`
5. **可能路径 B**：时间片用完，被打断，仍为 `PROC_RUNNABLE`
6. **唤醒**：等待事件发生，`wakeup_proc()` 将其变回 `PROC_RUNNABLE`
7. **退出**：调用 `exit()`，进入 `PROC_ZOMBIE`，父进程回收资源

## 2. 深入理解进程切换 [S08]

### 2.1 知识卡片：进程切换触发机制

| 字段 | 内容 |
|:---|:---|
| **名称** | 进程切换（Context Switch） |
| **要解决的问题** | 何时以及如何从一个进程切换到另一个进程 |
| **先修要求** | 中断机制、trap 处理流程 |

#### 核心问题

**进程切换究竟在什么情况下会发生？**

答案：大体分为两类——**主动调度**与**被动调度**。

### 2.2 主动调度 [S09]

#### 定义
主动调度指进程**自愿放弃 CPU**，显式表示自己需要等待或让出资源。

#### 触发场景

```
┌────────────────────────────────────────────────────────────────┐
│                        主动调度触发场景                         │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│  场景1：进程主动放弃 CPU                                        │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  do_wait()  ──▶  等待子进程结束                          │   │
│  │  do_sleep() ──▶  主动休眠                                │   │
│  │  do_yield() ──▶  主动让出 CPU                            │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                │
│  场景2：进程等待不可用资源                                      │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  lock()    ──▶  获取锁失败，阻塞等待                      │   │
│  │  I/O 操作  ──▶  等待磁盘/网络响应                         │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                │
│  场景3：内核线程显式调用                                        │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  schedule() ──▶  内核线程主动调用调度函数                  │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

#### 代码中的主动调度位置

| 函数 | 文件 | 原因 |
|:---|:---|:---|
| `do_exit` | proc.c | 进程退出，放弃 CPU |
| `do_wait` | proc.c | 等待子进程，放弃 CPU |
| `init_main` | proc.c | init 等待其他线程 |
| `cpu_idle` | proc.c | idle 等待就绪进程 |
| `lock` | sync.c | 获取锁失败时等待 |

#### 为什么需要主动调度？

> **关键洞察**：在 ucore 中，内核线程是**不可抢占**的。
> 
> 这意味着内核线程无法被其他内核线程强行打断。因此，必须依靠**主动让出 CPU** 的方式来避免死锁，维持系统整体的可调度性。

### 2.4 调度检查点：trap 函数 [S11]

在 `kern/trap/trap.c` 的 `trap` 函数中，有一段关键的调度检查代码：

```c
void trap(struct trapframe *tf)
{
    if (current == NULL)
    {
        trap_dispatch(tf);
    }
    else
    {
        struct trapframe *otf = current->tf;
        current->tf = tf;

        bool in_kernel = trap_in_kernel(tf);

        trap_dispatch(tf);

        current->tf = otf;
        
        // 【关键】只有从用户态陷入时才检查调度
        if (!in_kernel)
        {
            if (current->flags & PF_EXITING)
            {
                do_exit(-E_KILLED);
            }
            // 检查是否需要调度
            if (current->need_resched)
            {
                schedule();  // 执行调度
            }
        }
    }
}
```

#### 代码解读

1. **保存当前中断帧**：`current->tf = tf`
2. **判断是否在内核态**：`trap_in_kernel(tf)` 检查 SPP 位
3. **分发处理**：`trap_dispatch(tf)` 执行中断/异常处理
4. **调度检查**：只有**用户态陷入**时才检查 `need_resched`
5. **执行调度**：如果标志位为 1，调用 `schedule()`

> **为什么只在用户态陷入时检查？**
> 
> 因为内核态是不可抢占的。如果在内核态执行时被调度走，可能导致内核数据结构不一致或死锁。

#### 为什么使用 volatile？

```c
volatile bool need_resched;
```

`volatile` 关键字告诉编译器：
- 这个变量可能被**异步修改**（如中断处理程序）
- 不要对它进行优化（如缓存到寄存器）
- 每次访问都从内存读取最新值

## 4. 时钟中断与调度 [S13]

### 4.1 知识卡片：时钟中断

| 字段 | 内容 |
|:---|:---|
| **名称** | 时钟中断（Timer Interrupt） |
| **要解决的问题** | 周期性打断用户程序，使内核获得控制权 |
| **触发频率** | 由硬件定时器决定，通常每秒数十到数百次 |

#### 时钟中断处理代码

在 `kern/trap/trap.c` 的 `interrupt_handler` 函数中：

```c
case IRQ_S_TIMER:
    // 设置下次时钟中断
    clock_set_next_event();
    
    // 全局计数器加一
    ticks++;
    
    // 每 100 次打印一次
    if (ticks % TICK_NUM == 0)
    {
        print_ticks();
    }

    // 【Lab6 关键】调用调度器的 proc_tick 函数
    sched_class_proc_tick(current);
    
    break;
```

#### 调用链分析

```
时钟中断
    │
    ▼
interrupt_handler
    │
    ▼
sched_class_proc_tick(current)  ←── 在 sched.c 中
    │
    ▼
sched_class->proc_tick(rq, proc)  ←── 调用具体调度类的函数
    │
    ├──▶ RR_proc_tick()     (RR 调度)
    │
    └──▶ stride_proc_tick() (Stride 调度)
```
[Fig·S13-1]: 时钟中断到调度器的调用链

### 4.2 sched_class_proc_tick 函数

```c
void sched_class_proc_tick(struct proc_struct *proc)
{
    if (proc != idleproc)
    {
        // 对于非 idle 进程，调用调度类的 proc_tick
        sched_class->proc_tick(rq, proc);
    }
    else
    {
        // idle 进程总是需要调度（让出 CPU 给其他进程）
        proc->need_resched = 1;
    }
}
```

#### 为什么 idle 进程特殊处理？

> **关键洞察**：`idleproc` 是系统的"空闲进程"，当没有其他可运行进程时才运行。
> 
> 它的唯一任务是等待有进程可调度。因此，每次时钟中断都应该检查是否有新进程就绪，所以总是设置 `need_resched = 1`。

## 6. 易错点与比较 [S15]

### 6.1 常见误区

| 误区 | 正确理解 |
|:---|:---|
| "时钟中断直接触发进程切换" | ❌ 时钟中断设置标志位，trap 返回时才检查并切换 |
| "内核态也会被抢占" | ❌ ucore 的内核态是不可抢占的 |
| "RUNNABLE 就是正在运行" | ❌ RUNNABLE 包括就绪和运行两种子状态 |
| "SLEEPING 进程会被调度" | ❌ 只有 RUNNABLE 进程才能被调度 |

### 6.2 主动调度 vs 被动调度对比

| 对比项 | 主动调度 | 被动调度 |
|:---|:---|:---|
| 触发者 | 进程自己 | 外部（中断/系统调用） |
| 进程意愿 | 愿意让出 CPU | 不愿意（被迫） |
| 典型场景 | wait、sleep、lock | 时钟中断、系统调用返回 |
| 状态变化 | 常变为 SLEEPING | 可能保持 RUNNABLE |
| 代码位置 | do_wait、do_sleep | trap 函数 |

**答案**：C

**解释**：
- do_fork()：创建新进程，不改变当前进程状态
- do_yield()：主动让出 CPU，但状态仍为 RUNNABLE
- **do_wait()**：等待子进程，进入 SLEEPING 状态
- schedule()：执行调度，不直接改变状态

</details>

### 题目 3（开放题）
**题目**：为什么 ucore 选择在 trap 返回时检查调度，而不是在时钟中断处理函数中直接切换？

<details>
<summary>点击查看答案</summary>

**答案要点**：
1. **统一调度点**：将所有调度检查集中在一处，无论是时钟中断还是系统调用返回，都走同一条路径
2. **避免嵌套中断问题**：如果在中断处理中直接切换，可能导致中断处理不完整
3. **保证内核态不可抢占**：通过检查 `in_kernel` 标志，确保只有用户态陷入时才调度
4. **简化上下文管理**：在固定点保存和恢复上下文，逻辑更清晰

</details>
