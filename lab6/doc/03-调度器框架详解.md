## 1. 为什么需要调度器框架？[S16]

### 1.1 问题背景

在 Lab5 中，我们使用了简单的 FIFO（先进先出）调度策略。但在实际操作系统中：

- 不同场景需要不同的调度算法
- 交互式任务需要快速响应（RR 算法）
- 批处理任务需要高吞吐量（FCFS 算法）
- 某些任务需要更高优先级（Stride 算法）

### 1.2 设计目标

```
┌─────────────────────────────────────────────────────────────────┐
│                      调度器框架设计目标                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 【可扩展性】轻松添加新的调度算法，无需修改核心代码            │
│                                                                 │
│  2. 【解耦合】调度策略与调度框架分离                              │
│                                                                 │
│  3. 【可切换】运行时或编译时可选择不同调度算法                    │
│                                                                 │
│  4. 【统一接口】所有调度算法提供相同的操作接口                    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 2. sched_class 调度类结构体 [S17]

### 2.1 知识卡片：sched_class

| 字段 | 内容 |
|:---|:---|
| **名称** | sched_class（调度类） |
| **要解决的问题** | 提供统一的调度算法接口，实现调度策略与框架解耦 |
| **定义位置** | `kern/schedule/sched.h` |
| **类比** | 像"插座标准"——不同电器（调度算法）只要符合标准，都能插入使用 |

### 2.2 结构体定义

```c
struct sched_class
{
    // 调度类的名字（用于调试和识别）
    const char *name;
    
    // 初始化运行队列
    void (*init)(struct run_queue *rq);
    
    // 将进程放入运行队列
    void (*enqueue)(struct run_queue *rq, struct proc_struct *proc);
    
    // 将进程从运行队列取出
    void (*dequeue)(struct run_queue *rq, struct proc_struct *proc);
    
    // 选择下一个要执行的进程
    struct proc_struct *(*pick_next)(struct run_queue *rq);
    
    // 每次时钟中断调用
    void (*proc_tick)(struct run_queue *rq, struct proc_struct *proc);
};
```

### 2.4 为什么用函数指针？[S18]

**问题**：为什么要定义成函数指针，而不是直接写函数？

**答案**：实现**运行时多态**和**调度算法热切换**。

```c
// 方式1：直接写函数（不灵活）
void enqueue(struct run_queue *rq, struct proc_struct *proc) {
    // 只能实现一种算法
    RR_enqueue(rq, proc);  // 写死了！
}

// 方式2：函数指针（灵活）
struct sched_class *sched_class;

// 想用 RR 算法
sched_class = &default_sched_class;

// 想用 Stride 算法
sched_class = &stride_sched_class;

// 调用时：
sched_class->enqueue(rq, proc);  // 自动调用对应算法！
```

#### 优势总结

| 优势 | 说明 |
|:---|:---|
| 可扩展性 | 添加新算法只需实现接口，无需改框架 |
| 解耦合 | 框架代码与算法代码完全分离 |
| 可切换 | 只需改变指针指向即可切换算法 |
| 统一性 | 框架对所有算法使用相同方式调用 |

## 3. run_queue 运行队列结构体 [S19]

### 3.1 知识卡片：run_queue

| 字段 | 内容 |
|:---|:---|
| **名称** | run_queue（运行队列） |
| **要解决的问题** | 管理所有就绪态进程，供调度器选择 |
| **定义位置** | `kern/schedule/sched.h` |
| **类比** | 像"候车队伍"——乘客（进程）排队等候上车（获得 CPU） |

### 3.2 结构体定义

```c
struct run_queue
{
    // 【RR 使用】链表头，用于组织就绪进程
    list_entry_t run_list;
    
    // 运行队列中的进程数量
    unsigned int proc_num;
    
    // 最大时间片大小
    int max_time_slice;
    
    // 【Stride 使用】斜堆根节点
    skew_heap_entry_t *lab6_run_pool;
};
```

### 3.3 为什么需要两种数据结构？[S20]

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                     run_queue 两种数据结构对比                               │
├──────────────────────────────┬──────────────────────────────────────────────┤
│         链表 (run_list)       │            斜堆 (lab6_run_pool)              │
├──────────────────────────────┼──────────────────────────────────────────────┤
│                              │                                              │
│  适用算法：RR（时间片轮转）    │  适用算法：Stride（步进调度）                │
│                              │                                              │
│  特点：                       │  特点：                                      │
│  • FIFO 顺序                  │  • 按 stride 值排序                          │
│  • O(1) 入队/出队             │  • O(log n) 入队/出队                        │
│  • 队头即下一个进程            │  • 堆顶即最小 stride 进程                    │
│                              │                                              │
│  数据结构：                   │  数据结构：                                  │
│                              │                                              │
│  run_list ←→ P1 ←→ P2 ←→ P3  │         P1 (stride=5)                        │
│     ↑___________________↓    │        /    \                                │
│                              │   P2(10)    P3(15)                           │
│                              │                                              │
└──────────────────────────────┴──────────────────────────────────────────────┘
```
[Fig·S20-1]: 链表与斜堆对比

#### 设计原因

1. **RR 算法**需要按**入队顺序**调度，链表天然支持 FIFO
2. **Stride 算法**需要快速找到**最小 stride**，优先队列（斜堆）更高效
3. 两种结构**并存**，不同算法使用不同字段

### 3.4 Lab5 vs Lab6 的 run_queue 差异

| 对比项 | Lab5 | Lab6 |
|:---|:---|:---|
| 数据结构 | 仅链表 | 链表 + 斜堆 |
| 新增字段 | - | `lab6_run_pool` |
| 支持算法 | FIFO | RR、Stride 等 |
| 可扩展性 | 低 | 高 |

### 5.2 wakeup_proc：唤醒进程 [S25]

```c
void wakeup_proc(struct proc_struct *proc)
{
    assert(proc->state != PROC_ZOMBIE);  // 僵尸进程不能唤醒
    
    bool intr_flag;
    local_intr_save(intr_flag);  // 关中断，保证原子性
    {
        if (proc->state != PROC_RUNNABLE)
        {
            // 将进程状态改为就绪
            proc->state = PROC_RUNNABLE;
            proc->wait_state = 0;
            
            // 如果不是当前进程，加入运行队列
            if (proc != current)
            {
                sched_class_enqueue(proc);
            }
        }
        else
        {
            warn("wakeup runnable process.\n");
        }
    }
    local_intr_restore(intr_flag);  // 恢复中断
}
```

### 5.3 schedule：调度函数 [S26]

这是调度的核心函数！

```c
void schedule(void)
{
    bool intr_flag;
    struct proc_struct *next;
    
    local_intr_save(intr_flag);  // 关中断
    {
        // 清除当前进程的调度标志
        current->need_resched = 0;
        
        // 如果当前进程仍可运行，放回队列
        if (current->state == PROC_RUNNABLE)
        {
            sched_class_enqueue(current);
        }
        
        // 选择下一个进程
        if ((next = sched_class_pick_next()) != NULL)
        {
            sched_class_dequeue(next);  // 从队列移除
        }
        
        // 如果没有就绪进程，使用 idle 进程
        if (next == NULL)
        {
            next = idleproc;
        }
        
        // 记录运行次数
        next->runs++;
        
        // 切换到新进程
        if (next != current)
        {
            proc_run(next);
        }
    }
    local_intr_restore(intr_flag);
}
```

## 6. 调度封装函数 [S27]

### 6.1 封装层设计

框架函数不直接调用调度类函数，而是通过封装函数间接调用：

```c
// 封装 enqueue
static inline void
sched_class_enqueue(struct proc_struct *proc)
{
    // idle 进程不需要入队
    if (proc != idleproc)
    {
        sched_class->enqueue(rq, proc);
    }
}

// 封装 dequeue
static inline void
sched_class_dequeue(struct proc_struct *proc)
{
    sched_class->dequeue(rq, proc);
}

// 封装 pick_next
static inline struct proc_struct *
sched_class_pick_next(void)
{
    return sched_class->pick_next(rq);
}

// 封装 proc_tick（前面已介绍）
void sched_class_proc_tick(struct proc_struct *proc)
{
    if (proc != idleproc)
    {
        sched_class->proc_tick(rq, proc);
    }
    else
    {
        proc->need_resched = 1;
    }
}
```

#### 封装层的作用

```
┌─────────────────────────────────────────────────────────────────┐
│                      封装层作用                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 【统一入口】所有调度操作经由封装函数                         │
│                                                                 │
│  2. 【特殊处理】对 idleproc 进行特殊判断                         │
│                                                                 │
```

## 9. 易错点与比较 [S30]

### 9.1 常见误区

| 误区 | 正确理解 |
|:---|:---|
| "rq 是每个进程一个" | ❌ 目前 ucore 只有一个全局 rq |
| "enqueue 必须加到队尾" | ❌ 取决于调度算法（如 Stride 按优先级插入） |
| "pick_next 后自动出队" | ❌ 需要显式调用 dequeue |
| "idle 进程也在运行队列中" | ❌ idle 进程不入队，作为兜底 |

### 9.2 Lab5 vs Lab6 调度对比

| 对比项 | Lab5 (FIFO) | Lab6 (框架化) |
|:---|:---|:---|
| 调度策略 | 写死在代码中 | 通过接口动态绑定 |
| 可扩展性 | 差 | 优秀 |
| 时间片支持 | 无 | 有 |
| 优先级支持 | 无 | 支持（Stride） |
| 代码组织 | 混杂 | 分离清晰 |

## 10. 自测题

### 题目 1（判断题）
**题目**：在 ucore 中，sched_class 结构体中的函数指针必须全部实现，否则会编译错误。

<details>
<summary>点击查看答案</summary>

**答案**：❌ 错误

**解释**：C 语言不会强制检查函数指针是否为 NULL。如果某个函数指针未赋值或赋值为 NULL，编译可以通过，但运行时调用会导致崩溃。这是程序员的责任确保所有接口都正确实现。

</details>

### 题目 2（单选题）
**题目**：以下哪个操作会调用 `sched_class->enqueue`？

A. 进程刚创建完成时  
B. 进程被 wakeup_proc 唤醒时  
C. 进程时间片用完时  
D. 进程调用 exit 退出时

<details>
<summary>点击查看答案</summary>

**答案**：B

**解释**：
- A：进程创建后不一定立即入队
- **B**：wakeup_proc 会调用 sched_class_enqueue
- C：时间片用完只设置 need_resched，schedule 中才入队
- D：exit 不入队，进入 ZOMBIE 状态

</details>

### 题目 3（开放题）
**题目**：如果要实现一个"最短作业优先"（SJF）调度算法，你需要在 proc_struct 中添加什么字段？pick_next 函数应该如何实现？

<details>
<summary>点击查看答案</summary>

**答案要点**：

1. **新增字段**：
   ```c
   uint32_t estimated_runtime;  // 估计运行时间
   ```

2. **pick_next 实现思路**：
   - 遍历运行队列中所有进程
   - 找到 estimated_runtime 最小的进程
   - 返回该进程指针

3. **优化**：使用优先队列（斜堆），以 estimated_runtime 作为键值，可以将选择复杂度从 O(n) 降到 O(log n)

</details>
